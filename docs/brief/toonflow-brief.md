처음에는 직접 인스타툰을 제작하는 내부 도구로 시작하고, 이후 다른 작가들이 가입해 각자의 캐릭터·그림체·작업물을 관리하는 SaaS로 확장하는 방향이야.

### 제작실의 단계 이름

`Story → Storyboard → Illustrate → Review → Export`

- Story: 썰 분석과 각색
- Storyboard: 컷 분할과 대사 확정
- Illustrate: AI 이미지 생성과 선택
- Review: 말풍선, 품질, 개인정보 검수
- Export: 인스타그램 게시용 파일 출력

이 흐름을 TOONFLOW의 핵심 제품 경험으로 일관되게 사용하면 좋아.

# 7. Firebase 기반 SaaS MVP 설계

TOONFLOW를 나중에 다른 작가들도 사용하는 서비스로 만들려면, 지금부터 개인용 도구가 아니라 워크스페이스 단위의 SaaS로 설계하는 게 좋아.

단, 초기에는 실제로 본인 혼자 사용하더라도 데이터 모델과 보안 규칙에 `workspaceId`를 포함해 두면 나중에 여러 사용자로 확장할 때 마이그레이션 부담을 줄일 수 있어.

## 7-1. Firebase 구성

| Firebase / Google Cloud 기능 | TOONFLOW에서의 역할             |
| -------------------------- | -------------------------- |
| Firebase Hosting           | Vue 앱 배포                   |
| Firebase Authentication    | 회원가입, 로그인, 계정 관리           |
| Cloud Firestore            | 워크스페이스, 제보, 에피소드, 컷, 작업 상태 |
| Cloud Storage for Firebase | 원본·생성 이미지, 최종 결과물          |
| Cloud Functions 2nd gen    | AI 호출, 작업 생성, 이미지 렌더링      |
| Firebase App Check         | 지원 환경에서 비정상 요청 방어          |
| Cloud Tasks                | 이미지 생성 작업의 지연 실행과 재시도 제어   |

Cloud Tasks는 Firebase 자체 제품이라기보다 연계 가능한 Google Cloud 서비스야. 초기에는 Firestore 기반 작업 큐로 시작하고, 작업량이 늘어날 때 도입해도 돼.

## 7-2. Firestore 컬렉션 구조

```
users/{userId}
workspaces/{workspaceId}
  members/{userId}
  settings/{settingId}

submissions/{submissionId}
episodes/{episodeId}
  storyVersions/{versionId}
  characters/{characterId}
  panels/{panelId}
    versions/{versionId}

stylePresets/{presetId}
aiJobs/{jobId}
consentRecords/{consentId}
```

주요 문서에는 `workspaceId`를 포함해 각 워크스페이스의 데이터가 섞이지 않도록 해.

예를 들어 에피소드 문서는 다음과 같은 구조가 될 수 있어.

```
interface Episode {
  workspaceId: string;
  title: string;
  status:
    | "story"
    | "storyboard"
    | "illustrate"
    | "review"
    | "export";
  targetPanelCount: number;
  tone: string;
  stylePresetId: string | null;
  currentStoryVersionId: string | null;
  createdAt: Timestamp;
  updatedAt: Timestamp;
}
```

여러 작가가 사용하는 SaaS로 확장할 때는 단순히 화면에서 워크스페이스를 선택하는 것으로 끝나면 안 돼. Firestore Security Rules와 서버 함수에서 실제 사용자 권한을 검증해야 해. 특히 AI 생성 API는 클라이언트가 전달한 `workspaceId`만 믿어서는 안 되고, 인증된 사용자의 소속을 확인해야 해.

## 7-3. AI 작업 처리 방식

추천하는 흐름은 다음과 같아.

1. 프론트엔드가 이미지 생성 요청을 보낸다.
2. Cloud Functions가 인증과 권한, 생성 한도를 확인한다.
3. `aiJobs/{jobId}` 문서를 생성한다.
4. 비동기 작업자가 AI 이미지 API를 호출한다.
5. 생성 결과를 Cloud Storage에 저장한다.
6. Firestore에 결과 경로와 작업 상태를 기록한다.
7. Vue 화면은 작업 상태 변경을 구독해 진행 상황을 표시한다.

이 구조에서는 이미지 생성 요청과 실제 생성 작업이 분리돼. 브라우저를 닫아도 작업 상태를 유지할 수 있고, 실패한 작업을 재시도하거나 비용을 집계하기도 쉬워져.

이미지 생성은 동일 요청이 중복 처리되지 않도록 작업 ID와 재시도 정책을 설계하고, 재시도 시에도 무조건 새로운 유료 생성 요청을 발생시키지 않도록 주의해야 해.

```
}
```

실제 구현 시에는 Tailwind CSS의 테마 토큰과 연결해서 사용하면 컴포넌트 간 디자인 일관성을 유지하기 편해. 다크 모드는 MVP에 포함하더라도 초기에는 기본 색상과 대비 규칙을 먼저 확정하는 게 좋아.

## 최종 추천

TOONFLOW는 다음 방향으로 정리하는 게 가장 좋아.

- 브랜드: TOONFLOW
- 슬로건: Stories in. Comics out.
- 한국어 메시지: 이야기를 넣으면, 웹툰이 완성된다.
- 디자인: Ink Navy + Flow Coral + Warm Canvas
- 프론트엔드: Vue 3 + TypeScript + Vite
- 백엔드: Firebase Authentication, Firestore, Storage, Cloud Functions
- 핵심 제품: Studio 중심의 스토리·콘티·AI 이미지 제작 워크플로
- 확장 전략: 1인 운영으로 검증한 뒤 워크스페이스 기반 SaaS로 확장

첫 번째 개발 목표는 로그인 화면이나 대시보드 자체가 아니라, 썰 하나를 입력해 AI 각색, 컷별 이미지 생성, 말풍선 합성, 최종 이미지 ZIP 출력까지 성공하는 수직 기능을 만드는 거야. 이 경로가 완성되면 나머지 관리 화면은 그 위에 점진적으로 확장할 수 있어.
